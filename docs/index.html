What SIA does

A control plane for agentic work

SIA does not replace your model or IDE. It gives the host a shared, inspectable contract and saves workflow state under .sia/.

↻

Durable re-entry

sia next --json restores the current mode, stage, owner, tasks, and required action after a fresh chat or context compaction.

⋈

Parallel agent safety

Independent tasks can run together only when their canonical file ownership does not overlap— including parent/child and Windows case aliases.

✓

Independent review

Implementation and review carry separate caller-attested host run identities. Integration is blocked until every task is reviewed.

◇

Evidence-gated stages

Specs, plans, skills, reports, and integration records must exist before the workflow advances. Chat claims are not evidence.

∞

Self-improvement loop

PASS/DEVIATION events become scoped, provenance-bearing rules. Preflight checks load them before related work; convergence tracks recurrence.

⇄

Plugin coexistence

BMAD, Superpowers, MCP, native skills, and custom instructions remain available. Assign stage ownership instead of replacing another framework.

Choose the control level

Three runtime modes

Runtime mode is independent of the intake approach you choose for an existing project.

LOWEST CONTROL

Advisory

SIA owns feedback capture, standing rules, preflight, and convergence. Use this when BMAD, Superpowers, or your team already owns planning and execution.

sia init --mode advisory
PLANNING CONTROL

Planning

SIA owns intake, specification, project instructions, generated skills, and plan. A different framework or human team can execute.

sia init --mode planning
FULL CONTROL

Orchestrator

SIA owns the full evidence pipeline and coordinates host-native implementers and reviewers. It still does not impersonate a vendor agent API.

sia init --mode orchestrator
Quick start

Install, initialize, resume

Install the Python package

Python 3.10 or newer is required.

PowerShell / terminal 
python -m pip install sia-package==0.2.0

Open the target project

Run SIA from the actual repository root. Choose one runtime mode.

cd path/to/your-project
sia init --mode orchestrator
sia doctor

Install one host launcher

Claude, Codex, Kiro, and Antigravity have collision-safe, opt-in adapters. Gemini CLI uses the manual host-neutral flow documented below.

sia adapter install --host claude
# or: codex | kiro | antigravity

Ask the host to resume SIA

The JSON packet is the durable source of workflow position.

sia next --json

Operating model

The persistent SIA pipeline

Approval gates wrap every stage. The current stage is persisted; the assistant does not infer it from conversation memory.

02SpecApproved architecture
03InstructionsProject rules
04SkillsEvidence-derived pack
05PlanFiles and interfaces

Advancing evidence-gated stages

Ask what comes next

sia status
sia next --json

Every host follows the same packet, so changing tools does not reset the process.

Attach the artifact

sia advance --evidence docs/specs/export.md

Specification, instructions, skills, and plan stages require project-local evidence paths.

Orchestrator mode

Prepare → dispatch → review → integrate

SIA records caller-attested host identities and enforces ordering. The actual agent is spawned by Claude, Codex, Kiro, Antigravity, or another native harness.

1 · Prepare exclusive ownership 
sia task prepare \
  --task backend \
  --brief sdd/backend-brief.md \
  --files src/api.py

sia task prepare \
  --task frontend \
  --brief sdd/frontend-brief.md \
  --files src/App.tsx
2 · Record the native implementer
sia task dispatch \
  --task backend \
  --host kiro \
  --agent-id backend-implementer \
  --native-run-id <run-id>
3 · Attach report and independent review
sia task finish \
  --task backend \
  --report sdd/backend-report.md \
  --review sdd/backend-review.md \
  --reviewer-agent-id backend-reviewer \
  --review-native-run-id <review-run-id>
4 · Certify the combined result
sia integration --evidence sdd/integration.md
sia advance
What SIA rejects: overlapping paths, project-root ownership, paths outside the repository, the same implementer/reviewer identity, empty reports, integration before all reviews, and stale integration after the task set changes.
Feedback loop

Turn verified mistakes into scoped rules

Record outcomes

sia record \
  --outcome pass \
  --signal review \
  --context "Approved without correction" \
  --severity low

sia capture \
  --signal review-finding \
  --context "Controller touched an owned file" \
  --severity high \
  --error-class ownership-breach

Add and apply an approved rule

sia rule add \
  --text "Never edit dispatched task files" \
  --scope "src/*.py" \
  --severity high \
  --error-class ownership-breach \
  --source-event <event-id>

sia preflight --scope src/api.py
sia convergence

Medium/high matching rules require acknowledgment. Rules keep source event, evidence, severity, error class, scope, introduction date, and active/retired status.

BMAD, Superpowers, MCP

Share ownership instead of replacing tools

SIA's default framework policy is bridge. Existing framework files remain off limits.

Let BMAD own planning

sia owner --stage plan --to bmad
sia next --json

The packet tells the host to obtain BMAD's artifact before SIA advances.

Use only the learning loop

sia init --mode advisory
sia capture ...
sia preflight --scope src/auth.py
sia convergence

Other frameworks own the delivery process while SIA maintains project feedback.

Files and trust boundary

What is stored where

.sia/ ├── config.json # mode, framework policy, owners ├── state.json # stage, tasks, integration ├── events.jsonl # append-only outcomes ├── rules.json # active and retired rules ├── project.lock # cross-process serialization └── runs/ └── <run-id>/ ├── tasks/ └── integration.md

Commit intentionally

SIA runtime evidence can contain user corrections, paths, and review context. Review it for secrets before committing. Generated project artifacts—specs, plans, skills, and selected sdd/ mirrors—are normal project history.

Trust boundary

SIA checks ordering, path ownership, evidence presence, reviewer separation, and state consistency. It cannot cryptographically prove a vendor agent ran; native IDs are supplied by the host/controller.

Troubleshooting

Common questions

SIA says the project is not initialized
Run sia init --mode advisory|planning|orchestrator from the project root, then sia doctor.
The host did not invoke SIA automatically
This is intentional. Adapters are explicit to avoid monopolizing unrelated prompts. Invoke /sia where supported, or ask the host to run sia next --json.
Gemini CLI has no install adapter
Use the host-neutral packet and optional GEMINI.md activation rule above. Do not install the Codex/Antigravity adapter into Gemini paths.
SIA blocks a second parallel task
Its owned path intersects an active task. Sequence the work or give a later integration task exclusive ownership of the shared file.
Preflight exits with code 2
A matching medium/high standing rule needs acknowledgment. Review the rule and use --acknowledge <rule-id> only after approval.
I use BMAD or Superpowers
Choose advisory mode or assign individual stages with sia owner. SIA should not edit those frameworks' files.
Can SIA spawn agents by itself?
No universal vendor API exists. The host performs the actual spawn; SIA records caller-attested identities and enforces the common evidence contract.
