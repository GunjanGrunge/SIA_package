# Cost-aware multi-agent orchestration with unsafe release gates

> **Status as of 0.3.1 (2026-09-24).** This review predates fixes that landed
> with the Claude Code plugin. The review text below is preserved unedited.
>
> | Finding | Status |
> |---|---|
> | Critical — hard-budget bypass | **Fixed.** Reproduced against 0.3.1 and not present: an overrun is terminal whether it happens on the first receipt or the final one, later receipts are rejected, and integration is blocked. Guarded by `tests/test_runtime_behaviour.py`. |
> | "Validation is pattern-based rather than behavioral" | **Partly addressed.** Behavioural tests now drive the real CLI; the pattern validator remains alongside them. |
> | All High findings | **Not re-verified.** Treat as open until each is checked against current code. |

SIA 0.3 adds routed native-host and standalone operations, persisted plans and receipts, budget accounting, independent review, and receipt-bound integration. Several gates can be bypassed after planning: budget exhaustion can become successful completion, hashed inputs can change without invalidating execution, and stage ownership is not rechecked when work runs. Standalone execution buffers output without a real bound and does not terminate children on cancellation, while an inline prompt option exposes project content through process arguments. Integration evidence and strong-tier configuration do not enforce the release documentation's guarantees, and the added validation is pattern-based rather than behavioral.

Watch for: **confirmed, Critical** hard-budget bypass; **confirmed, High** mutable hashed briefs, stale integration receipts, ownership-transfer bypass, unbounded/cancellation-unsafe subprocesses, inline prompt disclosure, silent strong-to-current routing, and nonfunctional release validation.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed, Critical:** budget updates are serialized, but the receipt transition first marks an overrun and then replaces it with `complete` when the last operation finishes. Native receipts are also accepted while the plan is already `budget-exceeded`, so a run can exceed its ceiling, continue reviewing, and pass the integration gate.

**Confirmed, High:** the dispatch plan hashes each copied brief, but neither standalone launch nor native receipt ingestion compares the current brief to that hash. The plan also omits the standalone worker command and environment policy, so the immutable hash does not describe all inputs that determine what process executes.

**Confirmed, High:** standalone workers use `create_subprocess_exec`, but `communicate()` accumulates complete stdout and stderr before retaining the final 1 MB. Cancellation has no cleanup path, and the supported `{prompt}` argument places the full brief and implementer report in the OS-visible command line.

**Confirmed, High:** integration records receipt hashes once but never revalidates them before advancing, and receipts do not bind report content hashes. Evidence can therefore change after integration while the execution stage still advances successfully.

**Confirmed, High:** execution ownership is checked only when the plan is created. Transferring the execution stage to another framework afterward does not prevent standalone launch or native receipt ingestion from continuing under SIA.

**Confirmed, High:** configuration requires only cheap and current models; an omitted strong model silently aliases current. High-risk and complex operations can consequently be labeled `strong` while requesting the current model, contradicting the exact three-tier configuration and escalation claims.

**Confirmed, High:** no test executes the new orchestration behavior, and the repository's direct validation command currently fails. The release checks therefore neither gate the confirmed runtime failures nor produce a clean release result.

<summary>Details</summary>

## Hard-budget exhaustion can transition back to successful completion

**Confirmed, Critical.** `apply_orchestration_receipt` adds normalized usage and sets the orchestration status to `budget-exceeded`, then immediately computes operation statuses and unconditionally sets the plan to `complete` when all operations are complete (`src/sia/core.py:818-825`). It does not reject a new receipt when the existing orchestration status is `budget-exceeded`, so native-host review can continue after an implementer crosses the ceiling. Once the final reviewer receipt arrives, integration accepts the run because `record_integration` checks only for status `complete`.

A temporary-project reproduction planned one task below a 10,000-token ceiling, submitted an 11,000-token implementer receipt, then submitted an 11,000-token reviewer receipt. The first result reported `budget-exceeded`; the reviewer was accepted and the final result reported `complete` with 22,000 used tokens. Reproduce through the CLI by creating a native plan with low estimates, submitting an over-ceiling implementer receipt, then submitting the ready review receipt and running `sia integration`.

The completion transition must never override `budget-exceeded`, and receipt ingestion/scheduling must fail closed once the hard ceiling is reached. The check must remain inside the existing project lock so concurrent receipts cannot reserve or consume past the stop independently.

## The immutable plan does not enforce its hashed execution inputs

**Confirmed, High.** Plan creation stores `brief_sha256` for every operation (`src/sia/core.py:600-614`), but `dispatch_plan` validates only the JSON plan's own hash (`src/sia/core.py:682-690`). `_run_operation` reads the current brief without checking `brief_sha256` (`src/sia/orchestration.py:112-116`), and native receipt ingestion likewise never verifies the copied brief before accepting evidence. In a temporary-project reproduction, editing `.sia/runs/.../tasks/t/brief.md` after planning made its hash differ from the operation's `brief_sha256`, while `dispatch_plan()` still accepted the plan.

The same hash omits the selected standalone worker `argv`, environment allowlist, and timeout. `run_standalone` reloads these values from current configuration after plan verification (`src/sia/orchestration.py:213-226`), so direct configuration changes can alter the approved executable without changing `plan_hash`; `request.json` records the resulting argv hash only after the attempt directory is created and launch is imminent. Reproduce by planning with one harmless worker, editing `.sia/config.json` to another command, and invoking the unchanged plan with `--approve-commands`.

The plan should snapshot or hash every execution-defining input and verify brief/config hashes immediately before every native dispatch/receipt and standalone launch. Command approval should identify the exact rendered executable/argv digest being approved.

## Standalone output, cancellation, and prompt handling are not bounded safely

**Confirmed, High.** `_run_operation` calls `process.communicate()` and only slices decoded output to 1 MB after the child exits (`src/sia/orchestration.py:164-182`). A worker producing large or continuous output can consume unbounded controller memory until timeout or OOM, despite the documentation claiming enforced output bounds. Reproduce with a configured worker that continuously writes to stdout; controller memory grows with produced output rather than staying near the documented bound.

**Confirmed, High.** The timeout branch kills the direct process, but cancellation has no `CancelledError`/`finally` cleanup around the subprocess. Interrupting `sia orchestrate run` while a provider CLI is active can leave that process running and consuming budget. Reproduce with a long-running worker, interrupt the CLI, and inspect the child process list; cleanup must terminate and await the child on timeout, cancellation, and unexpected controller failure, ideally including its process group/tree.

**Confirmed, High.** `{prompt}` is an allowed whole-argument placeholder and expands to the complete task brief plus the implementer report for review (`src/sia/routing.py:13-17`, `src/sia/orchestration.py:57-78,136-148`). This exposes potentially sensitive project content to process listings and command-line telemetry, and sufficiently large reports can exceed OS argument limits. Reproduce with a worker using `{prompt}` and inspect its command line; remove inline prompt support or require an explicit unsafe opt-in, and use access-controlled prompt files/stdin by default.

## Integration manifests are snapshots, not enforced bindings

**Confirmed, High.** `record_integration` hashes receipt files into `receipt_manifest` (`src/sia/core.py:500-526`), but `advance` checks only that integration exists and its `covered_tasks` matches the task IDs (`src/sia/core.py:253-268`). It does not rehash the plan, integration evidence, or receipts. Normalized receipts also store only a `report_path`, not a digest of the canonical report, so review/report content can change without changing a receipt at all.

A temporary-project reproduction completed orchestration, recorded integration, appended one byte to a manifested receipt, confirmed the current hash no longer matched the manifest, and then successfully advanced from execution to feedback. Reproduce similarly with a completed run, or mutate `orchestrated-report.md` after receipt ingestion. Advancement must recompute and compare the plan, integration evidence, exact receipt set, receipt hashes, and report/review hashes; any mismatch should invalidate integration.

## Stage ownership can change without stopping an existing SIA plan

**Confirmed, High.** `create_dispatch_plan` rejects non-SIA execution ownership (`src/sia/core.py:552-564`), but `run_standalone`, `apply_orchestration_receipt`, and their CLI entry points do not recheck current mode, stage, or owner. A user or plugin can create a plan under SIA, transfer execution with `sia owner --stage execution --to bmad`, and still run standalone commands or ingest native completion receipts.

Reproduce by creating either backend's plan, changing execution ownership, then invoking `sia orchestrate run` or `sia orchestrate receipt`. Every launch and receipt transition must revalidate current stage ownership under the same state lock; transferring ownership should suspend or invalidate the active plan.

## Strong routing silently aliases the current model

**Confirmed, High.** `validate_orchestration_config` requires only `models.cheap` and `models.current`; if `models.strong` is absent, it copies current into strong (`src/sia/routing.py:63-82`). `route_task` still labels high-risk/complex implementation and high-risk review as strong, so persisted routing reasons and tiers imply an escalation that did not happen.

A direct reproduction calling `validate_orchestration_config` with only cheap ID `cheap` and current ID `current` returns strong ID `current`. Configuration should require an explicit non-empty strong model, or documentation and plan output must state that strong is an intentional alias and prevent claims that high-risk work escalated.

## Release validation neither runs orchestration nor currently passes

**Confirmed, High.** The only new checks in `tests/validate_sia.py` search source and documentation for strings such as function names, `budget-exceeded`, and `create_subprocess_exec`; no test creates a plan, races receipts, launches/cancels a worker, verifies model transitions, or checks integration staleness. `python -m pytest -q` reports three passing tests, but `python tests/validate_sia.py` fails because `AGENT.md` and `guides/orchestration.md` miss required literal patterns.

Reproduce with those two commands from the repository root. Add behavior tests for the confirmed failures and make the documented release validator pass before publishing; syntax-presence checks cannot support the 0.3 correctness and security claims.
